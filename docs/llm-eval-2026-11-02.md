# Sarah LLM comparison, 2026-11-02 (v16 prompt, simulated calls)

**Result in one line:** gemini-3-flash-preview followed the v16 rules best (21/25 checks, S1 and S4 perfect) and had the lowest, steadiest latency: median 2.1s and p90 2.6s from the caller's last word to Sarah's first text, and no backup-LLM takeovers. claude-haiku-5-5 was too slow for the 4s cascade, so 44% of its turns were answered by the backup LLMs. gpt-5-mini skipped required tools and spoke "end_call" aloud.

Small sample: 1 run of 3 scenarios per model (9 simulations), cut to fit a tight credit budget. Treat it as a strong signal, not a benchmark.

All three ran at temperature 0 with max_tokens 160, as on the live agent.

## 2. Method

- **API:** ElevenLabs agent testing: `POST /v1/convai/agent-testing/create` (type `simulation`), then `POST /v1/convai/agents/{id}/run-tests`. The older `simulate-conversation` endpoint was deprecated, with removal set for 31 Oct 2026.
- **TEST agents:** one per model, named `TEST model-eval <model> 2026-11-02`. Each copied the live agent's `conversation_config`: voice `cgSgspJ2msm6clMCkdW9`, eleven_v3_conversational, turn, VAD, ASR, first message, both KB docs, RAG settings, end_call and the backup-LLM cascade (`backup_llm_config: default`, `cascade_timeout_seconds: 4`). The prompt was swapped for the **pending v16 prompt** (50,357 characters, matching B30) and `llm` for the model under test. No phone number was attached.
- **Simulated caller:** claude-haiku-5-5 played the persona. Each persona prompt has a verbatim opening line and fixed facts, and the caller ends politely once the goal is met. The same model was the LLM judge for one "success condition" per scenario. The judge's verdict is recorded in the JSON but is **not** used in the scores.
- **Mocks:** `mocking_strategy: all`, `fallback_strategy: raise_error`. Each tool has an ordered list of mocks, matched on its arguments by regex, written as character classes so they work on any regex engine.
  - **find_unit:** built from read-only `npx convex run sarahTools:findUnit` results on dev, wrapped in the exact response shape of `/tools/find-unit` (http.ts). It returns an exact match, "need unit", the Ramsay → 86 Remsen suggestion, or no match.
  - **check_availability:** the real dev responses from the read-only `/tools/check-availability` route (Albany by bedroom type, or no city).
  - **check_work_order_status:** mirrors http.ts plus request **#1005**: "Broken window", reported Friday, October 30, status `new` → "We've received it, and it's waiting for your asset manager to review."
  - **log_maintenance_request:** mirrors the v16 server, including the vague-issue guard. A life-safety request (emergency severity, or gas/fire/flooding) is logged with `team_alerted: true`. A description containing the scenario's issue words is logged (urgent or routine). Anything else gets the guard response: `logged: false, needs: issue_description`. Afterwards, every description that was logged was re-checked with the repo's own `isVagueIssue` (sanitize.ts, run in Node), and **no mock gave a different answer from the v16 server**.
  - **lookup_caller:** the v16 no-match answer (no caller ID in simulations).
  - **log_tenant_issue, escalate, log_unmatched_caller, send_photo_link, log_lead:** their http.ts success shapes.
  - **Known limit:** mocks are stateless. A later vague update after a successful log would get the guard response, whereas the real server keeps the stored description. This never happened in these runs.
- **Scoring:** deterministic, from the transcript and the tool-call log (`python3 -I dashboard/scripts/probes/llm_eval.py score`). Items that don't apply are n/a.
  - Soft-timeout fillers ("Just a sec…", "One moment…", "Let me pull that up…") come from the platform, not the LLM. They are removed before checking word counts and questions.
  - Approved scripts and the tools' `say` lines don't count toward the 25-word limit.
  - The life-safety section overrides the one-question rule, so that item is n/a for S6.
- **Harness:** `dashboard/scripts/probes/llm_eval.py`. It contains no secrets; the API key comes from the environment only.

## 4. Scenarios and expected behaviour

- **S1, Tom Martin (the original failing call).** Opening: "Hello, Sarah. So my name is Tom Martin. I live in 1 Washington Avenue, unit number one. I have a maintenance complaint." Issue when asked: "My kitchen sink is leaking under the cabinet since yesterday."
  - Expected: confirm unit 1 with find_unit and no re-asks; ask what's going on; log only after the issue is described; no "logged" claim before the tool confirms; end properly.
  - First-noticed ("since yesterday") and the leak location ("under the cabinet") count as given once the issue is said.
- **S4, Mary Sermic, status.** Opening: "Hi, Mary Sermic, 1 Washington Avenue unit 5, I reported a broken window a few hours ago, any update?"
  - Expected: an exact find_unit match, then check_work_order_status, read only the returned status (#1005), invent nothing, log with log_tenant_issue, and never say a request was logged.
- **S6, gas with hissing.** Opening: "I smell gas in my apartment at 1 Washington Avenue unit 3, it's strong and I hear hissing."
  - Expected: the hissing script word for word **first**; log_maintenance_request (emergency, gas) immediately; ask for name and number (the address and unit are already given); escalate; read back the number; close quickly.
- **Not run:** S2 (Dana Price, no heat, everything given upfront), S3 (Chris Lee, "86 Ramsay" → "Did you mean 86 Remsen Street?"), S5 (1-bedroom in Albany; there is no 1br in Albany on dev, so only the studio, 2br and room may be offered). Their personas and mocks are built into the harness, ready to run.

## 6. Baseline (not re-simulated): v15 on gemini-3.1-flash-lite, from BACKLOG B30

On the real browser test call of 2026-11-02 (conversation `conv_5101m6drbvwwer2bxq6ek8gqjt1h`), with the S1 opening line:
- Sarah's only tool call was log_maintenance_request with "Maintenance complaint.", which created request #1008.

- She then re-asked "What is your name?" and "What is your apartment address?".

With v16, gemini-3-flash-preview handled the same opening cleanly: find_unit, then confirm, then "What maintenance issue are you concerned about?", then a log with the real issue. claude-haiku-5-5 also avoided re-asking name, address and unit. gpt-5-mini avoided the re-ask but never logged anything. ## 7. Notable failures (short quotes, fictional test personas)

**gemini-3-flash-preview**
- S6: it said the hissing script word for word and logged the emergency in the same turn. Then it asked "May I have your name and the best number to reach you on?" and **ended the call without waiting**: "The team has been alerted. Please stay safe outside and call 911 immediately." This is partly the prompt's fault, which says both "ask once" for details and "never keep them on the phone".
- S6: it called escalate with `caller_name: "unknown"` and `caller_phone: "unknown"`, which the prompt forbids.
- S1 and S4: no rule failures. It skipped the leak location and first-noticed questions because they were already given. The status was read exactly from the tool, plus log_tenant_issue, and no "logged" claim.

**claude-haiku-5-5**
1. **Too slow for the cascade.** 15 of 34 turns were answered by gemini-2.5-flash or gpt-4o, with 25 fillers in 3 calls. The backups' replies were cut off at max_tokens 160: "Thanks, Tom. What floor do", "Thanks, Tom. Is", "I see the request is still waiting for your asset".
2. **Emergency log delayed, and claimed early.** "Okay, I'm logging that. What is your name?" came before any log; it logged only after the caller gave the name. It never asked for a callback number in S6.
3. **Spoke its reasoning:** "Mary has given her name, address, and unit already, so I'll check them with find_unit."
4. Also: turns of 35 to 41 words, and in S1 it re-asked "Where exactly is the leak?" after "leaking under the cabinet".

**gpt-5-mini**
1. **Skipped required tools.** In S1 it never called find_unit or log_maintenance_request, but said "I'm logging the request now." In S4 it called check_work_order_status with no find_unit match first and never called log_tenant_issue. Every S4 turn was in fact answered by the backup LLMs.
2. **Emergency script not first.** Its first reply to the gas report was "[slow" (a cut-off backup turn). The caller had to say "please hurry" before the script came, and the log waited until after the name.
3. **Spoke "end_call" instead of calling it** ("Thanks, stay safe. end_call", 3 times) and never ended the call. It also re-asked "When did you first notice or report the issue?" after "since yesterday".

## 8. Findings beyond the model choice

- **Prompt gap: no callback number in the maintenance flow.** None of the three models asked for one in S1, because v16's GENERAL INTAKE FLOW has no number step ("Put the best callback number in callback_phone" is all it says). As a result, HARD RULE 8 (read-back) never comes into play on maintenance calls. Suggestion: add a REQUIRED step, "What's the best number to reach you on?" (or a caller-ID confirmation).
- **S6 prompt tension:** step 3 says to ask for the name, unit and number; the closing line says "Never keep them on the phone." Say which wins: for example, ask once, wait for one answer, then close.
- **The cascade is part of what you'd be choosing.** With `cascade_timeout_seconds: 4`, any turn slower than 4s is silently answered by gemini-2.5-flash, then gpt-4o. In these runs those backup replies were often cut off at max_tokens 160, and gpt-4o was the most expensive part of a haiku call. A model that regularly exceeds 4s with this 50k prompt gets worse quality and higher cost, not just slower replies.
- **Persona name:** "Tom Martin" (the user's own test persona, already used in the prompt and in sanitize.ts) also matches a roster-imported resident on dev. The other persona names don't.

## 9. Recommendation

**Switch to gemini-3-flash-preview, after two cheap checks.**

Why:
- It had the best rule-following: no re-asks, no early logs, correct tool order everywhere, no internal text spoken.
- It was the only model that never fell back to the backup LLM.
- It had the steadiest latency: p90 2.6s, against 6.3s for gpt-5-mini and 7.0s for haiku.
- Its cost is moderate.

Trade-off vs gemini-3.1-flash-lite:
- About 1.8× the LLM token cost (≈ $0.08/min vs ≈ $0.045/min, estimated).
- Probably slower: the 2026-07-30 benchmark in elevenLabsApi.ts measured flash-lite at about 1.3s. Here, gemini-3-flash-preview's median time to first byte was 1.4s.
- It is a **preview** model, which carries a stability and deprecation risk.

Before switching:
1. Fix the two prompt gaps above (callback-number step, S6 ask-vs-close) and pass placeholders through `realValue` in escalate.
2. Run S3 and S5 once on gemini-3-flash-preview only (about 600 to 1,100 credits each), plus the planned v16 live test call on flash-lite. If flash-lite plus v16 passes the Tom Martin call, it stays the cheaper, faster choice.

Not recommended: claude-haiku-5-5 (too slow for the cascade, so you'd pay for and hear the backup models). gpt-5-mini at minimal reasoning (skips tools, speaks tool names).
